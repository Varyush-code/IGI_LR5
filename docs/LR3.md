# Задание 3. План тестирования веб-приложения «Сайт зоопарка»

## 1. План тестирования

### 1.1. Цель тестирования

Целью тестирования является проверка соответствия веб-приложения «Сайт зоопарка» функциональным и нефункциональным требованиям, выявление ошибок в работе приложения, проверка корректности обработки пользовательских данных и разграничения доступа между различными категориями пользователей.

В процессе тестирования необходимо проверить:
- корректность отображения основных страниц сайта;
- работу регистрации, авторизации и выхода из учётной записи;
- разграничение прав посетителей, сотрудников и администраторов;
- корректность добавления, просмотра, изменения и удаления данных;
- работу разделов животных, сотрудников, билетов, кормления и помещений;
- корректность расчёта стоимости билетов;
- работу статистики и фильтрации;
- устойчивость приложения при вводе некорректных данных;
- соответствие интерфейса требованиям удобства использования.

### 1.2. Области тестирования

| Область | Требования | Обоснование |

Дополнительно проверяются нефункциональные требования:

- NFR-1 — удобство навигации и понятность интерфейса;
- NFR-2 — серверное разграничение доступа;
- NFR-3 — защита паролей и секретных настроек;
- NFR-4 — совместимость с современными браузерами;
- NFR-5 — разделение функциональности на Django-приложения;
- NFR-6 — корректная обработка отсутствующих данных и ошибок.

**Области, не подвергаемые углублённому тестированию:**

1. Производительность внешних сервисов, поскольку в предоставленной спецификации не указаны конкретные внешние интеграции.
2. Нагрузочное тестирование большого количества одновременно работающих пользователей — оно может быть выполнено в рамках отдельной лабораторной работы.
3. Полноценный аудит информационной безопасности и тестирование на проникновение — не входят в текущий объём работ.
4. Тестирование внутренней работы Django и сторонних библиотек, поскольку проверяется разработанное приложение, а не используемые фреймворки.

Исключение перечисленных областей из углублённого тестирования не означает полного отказа от проверки связанных нефункциональных требований.

### 1.3. Тестовая стратегия

Для проверки приложения используется комбинированная стратегия тестирования.

| Уровень тестирования | Содержание | Инструменты |
|---|---|---|
| Модульное | Проверка отдельных моделей, форм, представлений и функций | Django TestCase, unittest |
| Интеграционное | Проверка взаимодействия моделей, представлений, форм и базы данных | Django TestCase, Django Client |
| Сценарное | Проверка последовательности действий пользователя | Ручное тестирование, тест-кейсы |
| Системное ручное | Проверка приложения в целом | Браузер |
| UI-тестирование | Проверка интерфейса, отображения страниц и элементов управления | Google Chrome, Firefox |
| API-тестирование | Проверка HTTP-запросов, ответов сервера и проверки доступа | Postman, Django Client |
| Нагрузочное | Проверка работы приложения при увеличении количества запросов | Locust или JMeter |

**Виды тестирования:**

- функциональное — проверка выполнения требований;
- негативное — проверка поведения при некорректном вводе;
- позитивное — проверка корректной работы с допустимыми данными;
- регрессионное — повторная проверка после исправления дефектов;
- тестирование безопасности — проверка авторизации и разграничения доступа;
- тестирование совместимости — проверка в разных браузерах;
- тестирование удобства использования — оценка понятности интерфейса.

**Основные инструменты:**

1. Python — язык разработки и автоматизации тестов.
2. Django TestCase — автоматизация тестирования Django-приложения.
3. Django Client — имитация HTTP-запросов.
4. SQLite или используемая проектом СУБД — тестирование операций с данными.
5. Postman — проверка HTTP-запросов.
6. Google Chrome и Mozilla Firefox — ручное тестирование интерфейса.
7. Locust — возможное проведение нагрузочного тестирования.
8. PyCharm — разработка и запуск тестов.

### 1.4. Критерии тестирования

#### Критерии начала тестирования

Тестирование начинается при выполнении следующих условий:

- приложение успешно запускается;
- доступна тестовая база данных;
- настроены необходимые Django-приложения;
- выполнены миграции базы данных;
- подготовлены тестовые учётные записи;
- доступны основные страницы приложения.

Количественные критерии начала:
- успешность запуска приложения — 100%;
- успешность выполнения миграций — 100%;
- готовность тестовых данных — не менее 90%;
- доступность тестового окружения — 100%.

#### Критерии приостановки тестирования

Тестирование приостанавливается, если:
- приложение недоступно более чем в 20% попыток обращения;
- более 30% тест-кейсов невозможно выполнить из-за критических ошибок;
- обнаружена ошибка, блокирующая работу основных функций;
- тестовая база данных недоступна;
- отсутствуют необходимые тестовые данные.

#### Критерии возобновления тестирования

Тестирование возобновляется, когда:
- устранены блокирующие ошибки;
- доступность приложения составляет 100% при контрольных обращениях;
- тестовая база данных восстановлена;
- повторно выполненные блокирующие тесты проходят успешно;
- подготовлены необходимые данные.

#### Критерии завершения тестирования

Тестирование считается завершённым, если:
- выполнено не менее 95% запланированных тест-кейсов;
- успешно пройдено не менее 95% выполненных тест-кейсов;
- покрытие функциональных требований тест-кейсами составляет 100%;
- устранено 100% критических дефектов;
- устранено не менее 90% дефектов высокого приоритета;
- отсутствуют неисправленные дефекты, блокирующие основные пользовательские сценарии.

#### Приёмочные критерии

Приложение принимается, если:
- все функциональные требования высокого приоритета реализованы и проверены;
- основные пользовательские сценарии выполняются без критических ошибок;
- разграничение доступа работает корректно;
- операции с билетами и животными выполняются корректно;
- отсутствуют критические дефекты;
- выполнены установленные критерии завершения тестирования.

### 1.5. Метрики тестирования

Для оценки результатов используются следующие метрики.

**1. Процент успешного прохождения тест-кейсов**

Формула:

Процент успешного прохождения = (Количество успешно пройденных тест-кейсов / Количество выполненных тест-кейсов) × 100%.

**2. Процент выполнения тест-кейсов**

Процент выполнения = (Количество выполненных тест-кейсов / Общее количество запланированных тест-кейсов) × 100%.

**3. Покрытие требований тест-кейсами**

Покрытие требований = (Количество требований, покрытых тест-кейсами / Общее количество требований) × 100%.

**4. Процент устранения дефектов по важности**

Процент устранения дефектов = (Количество устранённых дефектов определённой важности / Общее количество обнаруженных дефектов данной важности) × 100%.

Метрики рассчитываются отдельно для критических, высоких, средних и низких дефектов.

## 3. Тест-кейсы

Для выполнения тестирования разработано 30 тест-кейсов.

Приоритеты:
- Высокий — критически важная функциональность;
- Средний — важные дополнительные функции;
- Низкий — функции, не влияющие непосредственно на основные пользовательские сценарии.

В качестве тестовых данных используются заранее подготовленные записи и тестовые учётные записи.

## 4. Выполнение тест-кейсов

Фактическое выполнение тест-кейсов проводится на запущенном Django-приложении с использованием подготовленной тестовой базы данных.

Для каждого тест-кейса фиксируются:
- фактический результат;
- статус выполнения;
- скриншот или видеозапись;
- комментарий при обнаружении ошибки.

Возможные статусы:
- PASS — тест пройден;
- FAIL — обнаружено несоответствие ожидаемому результату;
- BLOCKED — тест невозможно выполнить;
- NOT RUN — тест ещё не выполнялся.

## 5. Описание найденных дефектов

По предоставленным фрагментам исходного кода выявлены потенциальные дефекты. Они определены в ходе статического анализа и должны быть подтверждены выполнением соответствующих тест-кейсов.

### DEF-01. Отсутствие проверки данных животного при редактировании

**Краткое описание:** При редактировании животного отсутствует проверка введённых данных с использованием `full_clean()`.

**Подробное описание:**

Ожидаемый результат: При изменении животного система должна проверять корректность введённых значений, включая возраст и допустимые значения пола.

Фактическое поведение по анализу кода: В представлении `update()` после изменения атрибутов вызывается непосредственно `animal.save()`. Метод `save()` автоматически не выполняет проверку валидаторов модели.

Связанное требование: FR-2 (управление данными животных в рамках соответствующего модуля), NFR-6.

**Шаги воспроизведения:**
1. Открыть страницу редактирования животного.
2. Изменить возраст на значение больше 100.
3. Отправить форму.
4. Проверить сохранённые данные.

Воспроизводимость: Потенциально постоянная.

Важность: Высокая.

Срочность: Высокая.

Симптом: Возможность сохранения некорректных значений.

Возможность обхода: Проверять значения вручную перед отправкой формы. Это не заменяет серверную валидацию.

### DEF-02. Удаление животного выполняется без подтверждения

**Краткое описание:** Представление `delete()` удаляет животное непосредственно при обращении к нему.

**Подробное описание:**

Ожидаемый результат: Перед удалением пользователь должен подтвердить операцию, а удаление должно выполняться только при отправке соответствующего POST-запроса.

Фактическое поведение по анализу кода: В представлении сразу вызывается `animal.delete()` без проверки HTTP-метода.

Связанное требование: FR-2, NFR-2.

**Шаги воспроизведения:**
1. Открыть адрес представления удаления существующего животного.
2. Выполнить GET-запрос.
3. Проверить наличие записи в базе данных.

Воспроизводимость: Постоянная при обращении к соответствующему представлению.

Важность: Высокая.

Срочность: Высокая.

Симптом: Запись удаляется без подтверждения.

Возможность обхода: Не использовать прямой адрес удаления до исправления представления.

### DEF-03. Некорректный адрес перенаправления после удаления животного

**Краткое описание:** После удаления животного пользователь перенаправляется на корневую страницу сайта.

**Подробное описание:**

Ожидаемый результат: После удаления пользователь должен возвращаться в список животных.

Фактическое поведение по анализу кода: В представлении `delete()` используется `HttpResponseRedirect("/")`.

Связанное требование: FR-2, NFR-1.

**Шаги воспроизведения:**
1. Открыть представление удаления животного.
2. Удалить запись.
3. Проверить адрес страницы после удаления.

Воспроизводимость: Постоянная.

Важность: Низкая.

Срочность: Средняя.

Симптом: Пользователь попадает на главную страницу вместо списка животных.

Возможность обхода: Самостоятельно перейти в раздел животных через меню.

### DEF-04. Некорректное сообщение при отсутствии животного

**Краткое описание:** При обращении к несуществующему животному возвращается сообщение `Person not found`.

**Подробное описание:**

Ожидаемый результат: Пользователь должен увидеть корректное сообщение об отсутствии животного.

Фактическое поведение по анализу кода: В представлениях `update()` и `delete()` используется текст `Person not found`, который не соответствует предметной области приложения.

Связанное требование: FR-2, NFR-6.

**Шаги воспроизведения:**
1. Открыть страницу редактирования животного с несуществующим идентификатором.
2. Проверить сообщение сервера.
3. Повторить для удаления.

Воспроизводимость: Постоянная.

Важность: Низкая.

Срочность: Низкая.

Симптом: Отображается неподходящее текстовое сообщение.

Возможность обхода: Пользователь может вернуться к списку животных.

### DEF-05. Отсутствие явной проверки HTTP-метода при удалении

**Краткое описание:** Представление удаления сотрудника и животного должно защищать операции изменения данных от выполнения через GET-запросы.

**Подробное описание:**

Ожидаемый результат: Удаление данных должно выполняться только через POST-запрос с проверкой прав пользователя и CSRF-защитой.

Фактическое поведение по анализу кода: В представленном представлении `delete()` модели Animal удаление выполняется без проверки метода запроса. Для Employee используется стандартный `DeleteView`, но необходимо проверить шаблон подтверждения и настройки доступа.

Связанное требование: NFR-2.

**Шаги воспроизведения:**
1. Получить адрес представления удаления.
2. Выполнить GET-запрос.
3. Проверить, изменились ли данные.

Воспроизводимость: Постоянная для представления Animal.

Важность: Высокая.

Срочность: Высокая.

Симптом: Возможность выполнения операции удаления без подтверждающего POST-запроса.

Возможность обхода: Не обращаться к адресу удаления до исправления логики.

### DEF-06. Отсутствие проверки прав доступа в представлениях сотрудников

**Краткое описание:** В предоставленных классах представлений сотрудников отсутствуют явные ограничения доступа.

**Подробное описание:**

Ожидаемый результат: Только пользователи с необходимыми правами должны иметь возможность создавать, изменять и удалять сотрудников.

Фактическое поведение по анализу кода: В классах `EmployeesCreateView`, `EmployeesUpdateView` и `EmployeesDeleteView` не указаны `LoginRequiredMixin`, `PermissionRequiredMixin` или другие механизмы ограничения доступа.

Связанное требование: FR-8, FR-9, NFR-2.

**Шаги воспроизведения:**
1. Открыть браузер без авторизации.
2. Попытаться перейти к адресу создания сотрудника.
3. Проверить возможность отправки формы.
4. Повторить проверку с учётной записью посетителя.

Воспроизводимость: Требует проверки маршрутов и настроек проекта; по представленным классам защита не просматривается.

Важность: Высокая.

Срочность: Высокая.

Симптом: Потенциальная возможность изменения данных пользователями без необходимых прав.

Возможность обхода: Ограничить доступ к соответствующим адресам до исправления.

### DEF-07. Необходимость проверки корректности расчёта стоимости билета

**Краткое описание:** Требуется проверить точность расчёта итоговой стоимости билета при использовании промокодов.

**Подробное описание:**

Ожидаемый результат: Скидка должна корректно применяться к общей стоимости билета, а денежные значения должны сохраняться с предусмотренной точностью.

Фактическое поведение по анализу кода: Расчёт выполняется через умножение цены на `promocode.discount_percent` и деление на 100. Тип поля `final_price` и тип `discount_percent` в предоставленных фрагментах не показаны, поэтому наличие ошибки округления пока не подтверждено.

Связанное требование: FR-20, FR-17.

**Шаги воспроизведения:**
1. Создать активный промокод со скидкой 15%.
2. Выбрать выходной день и обе дополнительные услуги.
3. Применить промокод.
4. Проверить итоговую стоимость.

Ожидаемый результат для тестовых данных: 55 × 0,85 = 46,75 денежных единиц.

Воспроизводимость: Требует фактического выполнения.

Важность: Средняя.

Срочность: Средняя.

Симптом: Возможное некорректное округление денежной суммы.

Возможность обхода: Проверять итоговую сумму независимо до исправления, если расхождение подтвердится.
